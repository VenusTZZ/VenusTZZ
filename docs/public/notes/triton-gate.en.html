01 · The problem

Triton is device-agnostic; the glue code is hard-wired to CUDA

DeepSpeed's new fused ops (AutoEP's token permutation and row weighting, plus grouped GEMM, SwiGLU, fused RMSNorm, and fused RoPE) are all written in Triton, yet the guards and launch contexts around them assume CUDA.

1

Device guards hard-wire CUDA

RMSNorm, RoPE, and AutoEP token ops reject any non-cuda tensor outright, even though the kernel itself runs on the Triton runtime.

if x.device.type != "cuda": raise RuntimeError("runs CUDA kernels")
2

Launch contexts hard-wire torch.cuda

SwiGLU and RoPE switch devices with torch.cuda.device(), which crashes outright on CPU-only torch builds and non-CUDA accelerators.

with torch.cuda.device(x.device): kernel[grid](...)
3

The NPU door is permanently shut

The NPU accelerator's Triton switch returns False unconditionally, so even with the triton-ascend backend installed, every path falls back.

# npu_accelerator.py def is_triton_supported(self): return False # permanently off
4

Tests detect CUDA by device name

Module-level guards use device_name() == "cuda" and query bf16 capability through torch.cuda.get_device_capability(), which crashes on CPU-only torch builds.

if device_name() == "cuda": cap = torch.cuda.get_device_capability()
02 · The dilemma

So you just flip return False to True?

Flip the switch below to simulate “the backend-level gate opening all at once”. Watch closely: the backend is installed and most kernels run, but a few will crash outright in real training.

NPU backend-level Triton gate
// now: off (everything falls back)

fp8_gemmhardware lacks float8 tensor support; crashes at runtime
permute_rows_gatherdevice fault in multi-device runs
some fp32/fp16 kernelsdiffers from eager by 1 ulp

A single boolean cannot express per-kernel differences. A backend-level switch offers only two choices: the whole platform off (the old return False), or everything on, including the kernels that crash. What is needed is finer granularity — each kernel validated on its own.

03 · The solution

Three layers, three different questions

Can the backend run, can this kernel run, and what should be used when it cannot — a different layer answers each question, and every layer keeps the default CUDA path unchanged.

Drop every hard-coded CUDA check and route through one shared driver probe

A pure guard refactor — no kernel code touched. With no Triton backend installed, is_triton_available() is False and every gate stays closed.

Triton call site

swiglu / rmsnorm / rope / autoep…

→
accelerator abstraction

on_accelerator() / is_triton_supported(), with no device named explicitly

→
shared driver probe

standard driver probe: is the backend driver live

Key guarantees: CUDA behavior byte-for-byte unchanged no backend → all gates closed → fallback "same CUDA device" → "same device" NPU delegates to is_triton_available()

Every kernel proves itself once on the real device, the first time it runs

A minimal forward + backward is actually compiled and run, then cached per kernel:device:dtype, once per process. Use the buttons below to see the full run.

Engineering decisions

  • Probe failure is fail-closed: close the gate + a one-time warning; better to fall back than to kill a training run
  • Probes live in _probes.py instead of being scattered across call sites
  • Deterministic RNG builds the inputs, so results reproduce; the cache is thread-safe
  • Probing is deferred while a CUDA graph is being captured
  • DS_TRITON_KERNEL_GATE=0 falls back to the backend-level gate in an emergency
cache key: —

Annotation dispatch: the shared function is the fallback, platforms override it by name

In the op_builder style: a platform ships variants through its own triton_ops subpackage, and call sites do not change.

portable shared function (generic fallback)

Carries the @dispatch annotation and is itself the default implementation; always available when the platform module is absent.

@dispatch("swiglu_packed") def swiglu_packed_bwd(...): BLOCK_SIZE = 2048 # default
NPU subpackage deepspeed.ops.triton_ops.npu

The resolver asks triton_ops_dir() and loads the same-named override; re-exporting the original function counts as “no override”, so recursion is ruled out.

# npu/swiglu_triton.py def swiglu_packed_bwd(...): BLOCK_SIZE = 1024 # Ascend variant
// packed SwiGLU backward · 910B4
2048
the single packed element shape triggers triton-ascend MLIRCompilationError (unified-buffer overflow)
1024
compiles cleanly; forward and the remaining kernels stay at 2048; numerics verified on 910B4
