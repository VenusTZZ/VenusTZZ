01 · 问题起点

Triton 是设备无关的，胶水代码却是 CUDA 写死的

DeepSpeed 新的融合算子（AutoEP 的 token permutation、row weighting，以及 grouped GEMM、SwiGLU、fused RMSNorm、fused RoPE）都用 Triton 编写，但外围守卫和 launch context 全部假设 CUDA。

1

设备守卫写死 CUDA

RMSNorm、RoPE、AutoEP token ops 看到非 cuda tensor 直接拒绝，哪怕 kernel 本身跑在 Triton 运行时上。

if x.device.type != "cuda": raise RuntimeError("runs CUDA kernels")
2

Launch context 写死 torch.cuda

SwiGLU 和 RoPE 用 torch.cuda.device() 切设备，在 CPU 版 torch 和非 CUDA 加速器上直接崩。

with torch.cuda.device(x.device): kernel[grid](...)
3

NPU 大门永久关闭

NPU accelerator 的 Triton 开关无条件返回 False，即使 triton-ascend 后端已经装好，所有路径也只能走 fallback。

# npu_accelerator.py def is_triton_supported(self): return False # 永远关闭
4

单测按名字判断 CUDA

模块级守卫用 device_name() == "cuda"，bf16 能力通过 torch.cuda.get_device_capability() 查询，CPU 版 torch 上崩溃。

if device_name() == "cuda": cap = torch.cuda.get_device_capability()

一个布尔值表达不了 kernel 级差异。后端级开关只有两个选择：整个平台关着（旧的 return False），或者全开、包括会崩的 kernel。需要的是更细的粒度——让每个 kernel 被单独验证。

03 · 解决方案

三层机制，回答三个不同的问题

后端能不能跑、这个 kernel 能不能跑、跑不了该用什么实现——三个问题分别由三层回答，且每层都保持 CUDA 默认路径零变化。

去掉所有写死的 CUDA，统一走共享 driver probe

纯守卫重构，不碰任何 kernel 代码。没有装 Triton 后端时，is_triton_available() 为 False，所有 gate 保持关闭。

Triton 调用点

swiglu / rmsnorm / rope / autoep…

→
accelerator 抽象层

on_accelerator() / is_triton_supported()，不再点名设备

→
共享 driver probe

标准驱动探测：后端驱动是否在线

关键保证： CUDA 行为逐字节不变 无后端 → 全关 → 走 fallback "same CUDA device" 改为 "same device" NPU 委托给 is_triton_available()

每个 kernel 第一次使用时，在真实设备上自证一次

最小 forward + backward 实际编译运行，按 kernel:device:dtype 缓存，每进程一次。点下面的按钮看完整过程。

工程决策

  • 探测失败 fail-closed：关 gate + 一次性 warning，宁可回退不让训练崩
  • probe 集中在 _probes.py，调用点不散落
  • 确定性 RNG 构造输入，结论可复现；线程安全缓存
  • CUDA graph 捕获期间延迟探测
  • DS_TRITON_KERNEL_GATE=0 紧急回退后端级 gate
cache key: —

注解分发：公共函数即 fallback，平台同名覆盖

沿用 op_builder 风格：平台通过自己的 triton_ops 子包提供变体，调用点零改动。

portable 公共函数（generic fallback）

带 @dispatch 注解，自身就是默认实现；平台模块缺失时始终可用。

@dispatch("swiglu_packed") def swiglu_packed_bwd(...): BLOCK_SIZE = 2048 # 默认
