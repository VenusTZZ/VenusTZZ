First, understand the two inference phases

Autoregressive LLM inference runs in two stages: the prompt phase processes the entire input at once, while the decode phase generates one new token per step, in a loop. This PR's bugs happen to hide in each of the two. Toggle below to inspect both data paths.

02

RoPE: a different rotation for every position

Rotary position embedding groups a Q/K vector into adjacent element pairs, treats each pair as a 2D vector, and rotates it by an angle that grows with position. The further along the sequence, the more it turns — which is exactly how the model knows which token it is on. The demo below uses frequency pair 0, where angle (in radians) ≈ position × inverse frequency.

After the fix: the angle tracks position correctly, so each decode token gets its own absolute position.

Element pairing: the two layouts are not interchangeable

The cos/sin table layout decides which two elements form a rotation pair. If the table is interleaved but rotation uses split-half mode, the pairs are misaligned.

Inverse-frequency cache

Inverse frequencies depend only on rotary_dim and rope_theta, never on sequence length. The old code recomputed the whole pow chain in float64 and did an H2D copy on every forward; the new code caches fp32 values keyed by (rotary_dim, theta, device) and per step only does arange+offset, the outer product, and sin/cos.

Old: float64, recomputed every stepNew: fp32 cache · 1.3× faster

The 5 RoPE-path problems and their fixes

1
Decode rotation position is always 0seq_offset was accepted but never used, so every generated token rotated by position 0. Proof: offset 0 and offset 100 produce identical output.
Fix: position is driven by the KV buffer row count kv_len — a single source of truth
2
Prompt-phase element pairing is scrambledThe call to npu_rotary_mul omitted rotary_mode, so it defaulted to half pairing while cos/sin was the interleaved table from repeat_interleave(2).
Fix: pass 'interleave' explicitly to match the table layout
3
advance_tokens() is missingThe CUDA csrc increments the token counter after the last layer; the NPU side did not, so soft_len stayed at the prompt length.
Fix: call advance_tokens() after the last layer's forward
4
The rotate_half branch is entirely missingHF-style split-half rotation (Llama/GPT-NeoX/InternLM family) silently did nothing on NPU, leaving RoPE a no-op.
Fix: add the split-half branch, pairing j with j+dim/2 and reusing the same inv_freq
5
Angles recomputed on every forwardA full float64 pow chain plus an H2D copy every step, with no caching.
Fix: cache fp32 inv_freq, matching the v2 inference path
03

KV cache: from O(n²) rebuilds to O(1) single-row writes

Attention needs the K and V of every token so far. The old code called torch.cat for each generated token, reallocating and copying the entire history, then made a full contiguous copy into BSH layout. The new code preallocates a buffer in the layout the attention kernel consumes, so decode writes a single row and reads are zero-copy. Step through it to see the difference.

Capacity strategy: geometric growth

The CUDA op allocates once up front based on max_out_tokens; the NPU op is a static function with no config at construction time, and filling device memory for long contexts up front costs far too much. So it grows on demand: double the capacity when full, amortizing the copy to O(1); the prompt phase reserves min(2P, P+2048) headroom so the first decode step does not trigger a full copy. Reuse validates shape/dtype/device, not just length.

GQA reshape uses the wrong head count

K/V carry the KV head count, not the query head count. The old code reshaped with heads; under GQA (num_kv < heads), an element count that happens to divide evenly raises no error and silently scrambles the head dimension.

Old: reshape(..., heads)New: reshape(..., num_kv)

Layout alignment

The buffer stores [bsz, cap, num_kv_heads × head_dim] (BSH) directly, and attention reads the [:, :kv_len] zero-copy view; callers get back a transposed [bsz, heads, len, head_dim] view with the same semantics as the CUDA workspace tensor.
