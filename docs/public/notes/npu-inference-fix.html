01

先理解推理的两个阶段

大模型自回归推理分两段：Prompt 阶段一次性处理整段输入，Decode 阶段每次只生成一个新 token，反复循环。这个 PR 的 bug 恰好分别藏在这两段里。点击切换观察两条数据路径。

02

RoPE：给每个位置施加不同的旋转

旋转位置编码把 Q/K 向量按相邻元素两两分组，每组视为一个二维向量，旋转一个随位置增大的角度。位置越靠后，转得越多——这正是模型感知"第几个 token"的方式。下面的演示取第 0 对频率，角度（弧度）≈ 位置 × 逆频率。

元素配对：两种布局不能混用

cos/sin 表的排布方式决定了哪两个元素配成一对旋转。表是交错布局却用对半模式，配对就会错位。

逆频率缓存

逆频率只与 rotary_dim 和 rope_theta 有关，与序列长度无关。旧实现每次 forward 都用 float64 重算整条 pow 链并做 H2D 拷贝；新实现按 (rotary_dim, theta, device) 缓存为 fp32，每次只做 arange+偏移、外积、sin/cos。

旧：float64 每步重算新：fp32 缓存 · 1.3× 提速

RoPE 路径上的 5 个问题与修复

1
Decode 旋转位置恒为 0seq_offset 被接收但从未使用，每个生成 token 都用位置 0 的角度。证据：offset 填 0 与 100 输出完全相同。
修复：位置由 KV 缓冲行数 kv_len 驱动，单一事实来源
2
Prompt 阶段元素配对错乱调 npu_rotary_mul 未传 rotary_mode，默认 half 配对，但 cos/sin 是 repeat_interleave(2) 的交错表。
修复：显式传 'interleave' 模式匹配表布局
3
缺少 advance_tokens()CUDA csrc 在最后一层后递增 token 计数，NPU 侧没有，soft_len 一直停在 prompt 长度。
修复：最后一层 forward 后调用 advance_tokens()
4
rotate_half 分支完全缺失HF 风格对半旋转（Llama/GPT-NeoX/InternLM 类）在 NPU 上静默失效，等于 RoPE 白做。
修复：新增对半分支，j 与 j+dim/2 配对，复用同一 inv_freq
5
角度每次 forward 重算完整 float64 pow 链 + 每次 H2D 拷贝，无缓存。
修复：fp32 inv_freq 缓存，对齐 v2 推理模式
03

KV Cache：从 O(n²) 重建到 O(1) 单行写入

注意力需要历史所有 token 的 K 和 V。旧实现每生成一个 token 就 torch.cat 一次，重新分配并拷贝整段历史，再做一次 BSH 布局的 contiguous 全量拷贝。新实现预分配缓冲，直接存 attention 算子消费的布局，decode 只写一行、读取零拷贝。点击按钮单步观察差异。

容量策略：几何增长

CUDA op 构造时即按 max_out_tokens 一次性分配；NPU op 是静态函数、构造时拿不到配置，且长上下文一开始就吃满显存代价太大。因此按需扩容：容量不够就翻倍，扩容拷贝摊销为 O(1)；prompt 阶段预留 min(2P, P+2048) 头部空间，避免第一个 decode 就触发整段拷贝。复用时校验 shape/dtype/device，而不只是长度。

GQA reshape 用错头数

K/V 携带的是 KV 头数而非 query 头数。旧代码用 heads 去 reshape，GQA（num_kv < heads）下元素数碰巧能整除时不报错，直接把 head 维度静默打乱。

旧：reshape(..., heads)新：reshape(..., num_kv)

布局对齐

缓冲直接存 [bsz, cap, num_kv_heads × head_dim]（BSH），attention 读 [:, :kv_len] 零拷贝视图；返回给调用方的是 [bsz, heads, len, head_dim] 转置视图，语义与 CUDA workspace 张量一致。
