Fixing empty shards and non-contiguous gradients in multi-query GPTBigCode when TP > 1

One PR fixes two orthogonal defects: a sharding mismatch (transformers 5.x exposing num_key_value_heads=1, leaving some ranks with empty attention) and HCCL rejecting non-contiguous transposed gradients from torch_npu. 01

Start with the physical layout of the fused weight

GPTBigCode uses multi-query attention (MQA): the model has only 1 KV head in total, and all query heads share the same K/V. Its fused projection c_attn packs Q, K, and V into a single weight, laid out as “query rows first, then the whole shared K/V block”.

Query rows: sharded by head (varies per rank) K/V block: replicated whole (every rank keeps a full copy)
c_attn.weight = [out_features, in_features], hidden = 32, heads = 4
Q h0
Q h1
Q h2
Q h3
K (shared, 8 rows)
V (shared, 8 rows)
out = 32 (Q) + 16 (K/V) = 48 rows　·　in = 32
  • Q rows are sharded: when TP splits the weight, _bigcode_type_transpose shards only this part, so each rank holds hidden/TP rows.
  • The K/V block is replicated: at any TP degree, every rank holds the full 16 K/V rows and never shards them.
  • Replication creates a gradient problem: each rank produces K/V gradients only for its own Q heads, so they must be summed with all-reduce; otherwise the K/V rows that should be identical would drift apart after the update.

Defect B: one matmul, two memory layouts

The K/V gradient all-reduce operates on a view carved out of the fused gradient by narrow(). CUDA's matmul backward returns a contiguous [out, in] gradient; torch_npu returns a transposed, non-contiguous layout. Both NCCL and HCCL reject non-contiguous collective inputs — this is independent of the transformers version, and NPU fails on 4.44.2 as well.

CUDA / NCCLcontiguous
grad (32, 32)　stride (32, 1)　narrow → KV (16, 32)
is_contiguous() = True　·　the view is contiguous row by row
narrow view→all_reduce in place→zero extra copies
NPU / HCCL (torch_npu)non-contiguous
grad (32, 32)　stride (1, 32)　clone() preserves the transposed layout
is_contiguous() = False　·　the KV view stays non-contiguous after narrow
narrow view→HCCL: Tensors must be contiguous

Branching after the fix: no backend hardcoding, decide by tensor layout

KV view numel == 0?→skip (the replicated block is empty on all ranks) | Contiguous?→all_reduce in place | Non-contiguous?→stage via .contiguous()→all_reduce→copy_ back into the autograd view

The code changes touch four files

The fix for defect A spans sharding metadata and engine validation, while defect B is contained inside the gradient hook; the change is limited to 413 insertions and 23 deletions.

fusedqkv_utils.py
  • Adds replicates_kv_block() to detect bigcodetype replicated layouts by scanning class names
  • Class names are derived from FUSED_QKV_TYPE_DICT, so new layouts need zero maintenance; avoids the O(n²) scan caused by stringifying subtrees
auto_tp.py
  • Replicated layouts: tp_meta overrides the shard count with num_attention_heads
  • KV head attributes stay whole and unsharded; num_key_value_groups is recomputed from the local Q shard
  • Falls back to the model's original value when an attribute is missing, remaining compatible with older transformers
engine.py
  • fail fast: when tp > the number of query heads, raise a RuntimeError with a fix suggestion before sharding
  • Non-replicated layouts keep the original warning path, leaving existing behavior unchanged
layers.py
  • Extracts _sum_replicated_kv_gradient() to choose in-place communication or a staged contiguous copy based on layout
  • Writes the result back into the view autograd consumes and skips empty K/V blocks

Known issue: double counting in gradient clipping (tracked in a separate issue, not changed by this PR)

The global norm counts the replicated K/V rows once on every TP rank. At TP=2 the c_attn norm is exactly √2× the single-device value; removing one redundant K/V count reproduces the single-device value exactly.

‖grad‖²_tp = ‖Q‖² + TP · ‖K/V‖²　　⇒　　c_attn norm at TP=2 = √2 × single-device value (measured 1.414×)

Also not covered: ZeRO stages 1/2/3 were confirmed in code only, not run on hardware; fp16/autocast is unverified; the generate and past-KV-cache paths are untested; the forward failure with non-MQA (multi_query=False) is a pre-existing issue, #8927.
