01问题：三个算子在 NPU 上整体缺席

ZeRO-3 把参数切片分散到各 rank，训练时需要反复 all-gather 拉权重、all-to-all 交换梯度，通信是主要瓶颈。ZeRO++ 用低比特量化把通信载荷压下来，但这些能力都依赖 Quantizer 算子；同时 Lion、LAMB 两个融合优化器也依赖各自的 fused op。NPU 后端三者皆缺，配置一开就在引擎初始化阶段崩溃。

初始化崩溃

FusedLion

"optimizer": {"type": "Lion"} 时 FusedLionBuilder().load() 抛 ValueError，Lion 训练在昇腾上无法启动。

初始化崩溃

FusedLamb

"type": "Lamb" 时同样落到未实现分支，LAMB 的 trust ratio 语义在 NPU 上没有对应入口。

初始化崩溃

Quantizer（hpZ / qgZ）

打开 zero_quantized_weights 或 zero_quantized_gradients，量化器加载失败，ZeRO++ 量化通信全部不可用。

为什么通信是 ZeRO 的瓶颈

hpZ · 量化权重 all-gather

fp16 权重按组做 int8 对称量化后再 all-gather，每卡每次拉取权重的字节数直接减半；到卡后反量化，训练计算仍保持 fp16/bf16。

qgZ · 量化梯度两阶段 all-to-all

梯度压成 int4 并按两阶段 all-to-all 布局重排：先机内交换、做 quantized_reduction（反量化→fp16 累加→再量化），再机间交换。

02根因：OpBuilder 后端分发与兜底逻辑

DeepSpeed 每个可加速算子都有一个 OpBuilder，按后端目录各自实现。后端缺哪个算子，名字就解析到 NotImplementedBuilder，调用 load() 立即抛错。切换下面的后端，观察三个算子在不同后端上的实现状态。

deepspeed.initialize()
└─ FusedLionBuilder / FusedLambBuilder / QuantizerBuilder
   └─ NotImplementedBuilder.load()
      ValueError: This op had not been implemented on NPU backend.

背景：PR #8054 先给 SUPA 后端补齐了这三个 builder，NPU 成为唯一缺口；本 PR 在 op_builder/npu/ 下新增同名模块并在 __init__.py 注册，分发时即命中真实实现。

03hpZ 工作流：int8 量化 → 搬运 → 反量化

量化值只作为通信载荷存在，绝不进入训练计算。逐步走一遍一个量化组的完整生命周期。

1 分组
2 求 scale
3 截断 clamp
4 字节搬运
5 反量化

关键契约：为什么必须是「向零截断」

scale  = 2^b / (2 · max(|x|))        # max 为 0 时 scale 取 1.0
params = 1 / scale                    # 每组实际发送的是 scale 的倒数（fp32）
q      = trunc(x · scale)             # 向零截断，对应 CUDA 的 static_cast
q      = clamp(q, -2^(b-1), 2^(b-1)-1)
# 若改成 round-to-nearest，每个量化值都会变 —— 混部集群里 CUDA 与 NPU 反量化结果不一致

05qgZ 工作流：int4 打包与两阶段 all-to-all

两个相邻量化值塞进一个字节：偶数元素放低四位、奇数元素放高四位，按有符号二进制补码解释。点击字节查看它的两个 nibble。

nibble 打包（有符号补码）

点击任意字节查看拆解…

取值范围 [−8, 7]；负数以补码形式占据 nibble，解包时做符号扩展。torch_npu 的 npu_anti_quant 把 int4 当无符号处理，与该格式不兼容。

swizzle_quant：组重排

量化后按目标 rank 对分组做置换，让每个目的卡收到的数据在内存里是连续一整段，all-to-all 可以整段搬运而不是碎片收发。

输入组 g:
 (z·pipeline+y)·C + x
输出槽位:
 y·P + (z % dpn)·nodes
       + z // dpn
z=分区 y=流水切片 x=组内序号

两阶段 all-to-all 与 quantized_reduction

阶段一机内 all-to-all（int4 打包字节）
reduce反量化 → fp16 累加 → 重新量化
阶段二机间 all-to-all（再量化后的载荷）
→→→
swizzle按目的卡连续布局的量化组
fp16 累加同机各 rank 梯度求和，控误差
落盘安全checkpoint 只存未量化权重

06两个融合优化器：契约对齐与链式 in-place

两者都是无状态纯 torch 模块，fp32 计算、写回参数原 dtype。链式 in-place 更新减少 kernel launch，是性能与可验证性的平衡点。

c = β1·m + (1−β1)·g
p *= (1 − lr·wd)          # 乘性权重衰减
p += lr · sign(c)         # c==0 时取 +lr 分支
m  = β2·m + (1−β2)·g      # 动量最后更新（c 用旧动量）

设计要点

符号更新与参考内核逐比特一致；overflow 标志置位时跳过整步。链式 in-place 在 910B4 上比显式两步算术快约 26%，且结果 bitwise 相等。

m = β1·m + (1−β1)·g
v = β2·v + (1−β2)·g²
denom = sqrt(v+eps) 或 sqrt(v)+eps
u = m/denom + wd·p
coeff = clamp(||p||/||u||, min, max)
p -= step_size · coeff · u

完整语义一项不少

trust ratio 的 max/min 系数 clamp、bias correction、两种 eps mode、零范数回退（系数取 1.0）。与 torch_npu 官方 NpuFusedLamb 同语义对照：一阶矩逐比特一致，参数差 1 ulp。

负面结论

机内场景 hpZ 反而更慢

实测 HCCL all_gather 4.7–16.2 GB/s，量化盈亏平衡带宽 14.4 GB/s；该机内链路上 hpZ 为 fp16 基线的 0.62–0.97×。收益依赖跨节点长链路，数据与环境已完整写入 PR。

已知偏差

除法 1 ulp 偏差

昇腾 fp32 除法约 5% 的值差 1 ulp。各 rank 同值、相对误差 ~1e-7 比量化误差 ~1e-2 小五个数量级，且线格式瞬态、不落 checkpoint，有界且安全。
